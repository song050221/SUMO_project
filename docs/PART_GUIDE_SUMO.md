## [SUMO] 0. 30초 요약

광진구 실제 도로망(OpenStreetMap, 차도 약 1만 8천 개 구간, 신호 197개)을 교통 시뮬레이터 SUMO로 옮기고, 시간당 차량 7,200대·보행자 약 900명을 흘린다.
그 위에서 "중앙 서버"가 모든 차량의 위치·경로를 알고 있다고 가정(V2N)하고,
① 사고를 감지하면 차마다 정지/감속/우회/원래 경로 유지를 판단하고,
② 60초마다 모든 차의 경로를 실시간 통행시간 기준으로 다시 계산하며,
③ 90초 뒤 넘칠 도로를 예측해 여유 있는 차를 미리 돌리고,
④ 교차로 신호 초록 시간을 대기열 비교로 배분한다.
결과는 웹 대시보드와 sumo-gui 화면으로 실시간 보여 주고, 신양초 어린이보호구역 사거리에는 실물 RC카 보드의 상황이 그대로 그려진다(디지털 트윈).

**1분 발표용 설명**
"저희는 광진구 도로망 전체를 SUMO라는 교통 시뮬레이터로 옮겼습니다. 여기서 차 7,200대가 달리는데, 중앙 서버가 모든 차의 경로를 알고 있다는 V2N 환경을 가정합니다. 사고가 나면 사고 도로 위의 차는 멈추고, 1~2칸 앞 차는 감속하고, 3~5칸 앞 차는 우회 경로를 계산합니다. 이때 우회가 오히려 늦으면 원래 경로로 기다리도록 비교까지 합니다. 사고와 별개로 60초마다 모든 차의 경로를 실시간 정체 기준으로 갱신하고, 90초 뒤 막힐 도로를 미리 예측해 분산시키며, 신호는 대기열이 긴 방향에 초록을 더 줍니다. 이 모든 판단이 대시보드에 차마다 '어떤 알고리즘이 적용됐는지, 도착 시간이 얼마나 바뀌었는지'로 표시됩니다. 그리고 신양초 사거리는 실물 보드와 연결돼, 실제 RC카가 보행자를 보고 멈추거나 우회하는 모습이 시뮬레이션에 그대로 나타나고, 보드를 벗어난 차는 시뮬레이션 차량이 되어 중앙 제어를 받으며 계속 달립니다."

## [SUMO] 1. 이 파트의 역할과 전체 시스템에서의 위치

### [SUMO] 1-1. 입력·출력

| 구분 | 내용 | 형식 / 위치 |
|---|---|---|
| 입력 | 도로망 원본 | OpenStreetMap `network/export.osm` → `netconvert -c network/gwangjin.netccfg` → `network/gwangjin.net.xml` |
| 입력 | 차량·보행자 수요 | SUMO `randomTrips.py` + `duarouter`로 생성한 경로 파일 (`network/routes.xml` 7,200대, `network/pedestrian_routes.xml`) |

| 입력 | 실물 보드 상황 | 차량 호스트가 보내는 `traffic_state` JSON, **UDP 9002, 초당 10회** (`configs/hardware_twin.json`의 `udp_port`) |
| 출력 | 차량 제어 | TraCI(SUMO 원격 제어 API)로 감속·정지·경로 변경·신호 시간 변경 |
| 출력 | 화면 | sumo-gui 창 + 웹 대시보드 `http://localhost:5000` (Flask + Socket.IO) |
| 출력 | 측정 결과 | `experiment_data/results.csv`(baseline vs treatment), `scripts/measure_congestion.py` 결과 JSON |

### [SUMO] 1-4. 이 파트가 없으면

- "중앙 제어가 도시 전체 교통에 어떤 영향을 주는가"를 보여 줄 수단이 없다(실물 보드는 사거리 하나, 차 2대).

|---|---|---|
| **SUMO 1.27.1** | 독일 항공우주센터(DLR)가 만든 오픈소스 미시 교통 시뮬레이터. 차 한 대 한 대의 가속·차선 변경·신호 대기를 계산 | 무료·학계 표준·실제 지도(OSM) 변환 도구 내장·파이썬 원격 제어(TraCI) 지원 |
| **TraCI** | 실행 중인 SUMO를 파이썬에서 매 초 조종하는 API | "중앙 서버가 차에 명령"을 코드로 그대로 구현 가능 |
| **netconvert** | OSM 지도를 SUMO 도로망으로 바꾸는 도구 | 설정 파일 하나(`gwangjin.netccfg`)로 누구나 똑같이 다시 만들 수 있음 |
| **Python + Flask + Socket.IO** | 대시보드 웹 서버와 실시간 화면 갱신 | 시뮬레이션과 같은 프로세스에서 바로 데이터를 보여 줄 수 있음 |
| **UDP** | 실물 보드 → SUMO 통신 | 초당 10회 최신 상태만 필요, 한두 개 유실돼도 다음 메시지가 덮어씀 → TCP 재전송 불필요 |

### [SUMO] 2-2. 핵심 개념 쉬운 말로

- **edge**: 교차로와 교차로 사이 도로 한 토막(방향별로 따로). "칸(hop)"은 edge 하나를 말한다.
- **baseline / treatment**: baseline = 중앙 제어 없음(각 차가 출발 전에 정한 최단 경로로만 감). treatment = 중앙 제어 전부 켬. 같은 차량·같은 난수(seed)로 둘을 비교한다.
- **seed**: 난수 시작값. 같은 seed면 같은 차가 같은 시각에 출발하고 같은 사고가 난다. 결과가 우연인지 보려고 seed를 여러 개 돌린다.
- **통행시간 페널티(adaptTraveltime)**: 라우터에게 "이 도로는 100만 초 걸린다고 쳐"라고 거짓 정보를 줘서 자연스럽게 피하게 하는 SUMO 표준 방법.
- **견인**: 180초 넘게 한자리에 낀 차를 지우는 것. 실제라면 견인차가 치우는 상황을 흉내 낸 현실 보정.
- **디지털 트윈**: 실물 보드에서 일어나는 일을 가상 사거리에 실시간으로 똑같이 재현하는 것.

### [SUMO] 2-3. 비유

- 중앙 제어 = **"도시 전체를 보는 관제탑 + 모든 차에 달린 내비"**. 일반 내비는 각자 최단 경로를 고르지만, 관제탑은 "지금 저 길로 다 몰리면 막힌다"를 알고 일부만 돌린다.
- 사고 대응 3단계 = **"사고 현장 앞 차는 멈추고, 바로 뒤 차는 속도를 줄이고, 멀리 있는 차는 미리 다른 길로"**. 소방차 출동 때 교통 통제와 비슷하다.
- 신호 배분 = **"줄이 긴 계산대에 직원을 더 배치"**.
- 견인 = **"고장 난 차를 치우는 견인차"**. 이게 없으면 시뮬레이션에서 한 번 낀 차가 영원히 도로를 막는다.

## [SUMO] 3. 논리 구조

### [SUMO] 3-1. 매 스텝(1초) 처리 순서

`scripts/dashboard_server.py:403` `simulation_loop()` 기준.

1. `traci.simulationStep()` — SUMO가 1초 진행.
2. 충돌 수·급제동(가속도 < -4.5 m/s², `dashboard_server.py:43`) 집계.
3. 대시보드 버튼 요청 처리(수동 사고, 차량 감지, 보행자 토글).
4. `HardwareTwin.step()` — 실물 보드 상황 반영(3-7).
5. `CentralServer.initial_optimization()` — 60초 지난 차만 경로 재계산(3-3).
6. `poll_all_zones()` — 사고 발생·감지 → alert 목록(3-2).
7. `decide_actions(alerts)` — 차별 명령(3-2).
8. `StuckVehicleRemover.step()` — 20초마다 180초 넘게 선 차 견인(3-5).
9. `execute_commands(commands)` — 명령 실행 + 우회/대기 비교(3-2).
10. `SignalController.step()` — 5초마다 신호 조정(3-4).
11. `PredictiveRerouter.step()` — 60초마다 정체 예측 우회(3-3).
12. 대시보드용 데이터 계산 후 Socket.IO로 전송, 실제 시간에 맞춰 대기(기본 1배속).

### [SUMO] 3-2. 사고 대응 (정지 / 감속 / 우회 / 원래 경로 유지)

**사고 발생 규칙** (`core/cctv_detector.py:24-31`, `update_accidents()` `:148`)
- 30초마다 1건, 30초 지속 → 새 사고가 나면 이전 사고는 풀림(항상 1건).
- 위치 = 지금 도로 위 모든 차의 **남은 경로에 가장 많이 들어 있는 도로**(앞으로 가장 많은 차가 지나갈 도로). `_busiest_upcoming_edge()` `:132`.
- 후보 조건: 차가 다닐 수 있는 도로, 20m 이상, 어린이보호구역 제외, 최근 5건 사고 도로 제외(`RECENT_ACCIDENT_EXCLUDE=5`).
- `[가정]` 실제 사고 빈도가 아니라 **스트레스 테스트**다. "사고가 가장 영향이 큰 곳에 계속 난다"는 최악에 가까운 조건.

**감지** (`poll_all_zones()` `:458`)
- CCTV 9곳 + 어린이보호구역 안: 사고(`detect_accidents` `:384`), 보행자(`detect_pedestrian_in_zone` `:415`), 정체(평균 속도 2 m/s 미만, `detect_traffic_anomaly` `:436`).
- 구역 밖 도로 사고: `detect_road_accidents()` `:182` — "V2N 차량 신고로 도로망 전역을 안다"는 가정.

**차량 분류** (`_classify_vehicles()` `:91`) — 사고 도로 기준 상류(거슬러 올라가는) 방향 칸 수로 나눈다.

| 차 위치 | 분류 | 명령 | 기준값 |
|---|---|---|---|
| 사고 도로 위 | `vehicles_in_hazard_edge` | **정지** (목표 속도 0) | — |
| 사고 1~2칸 앞 | `vehicles_nearby` | **감속** 5 m/s(18 km/h) | `NEARBY_HOPS=2` (`cctv_detector.py:21`), `PREVENTIVE_SLOWDOWN_SPEED=5.0` (`decision_policy.py:11`) |
| 사고 3~5칸 앞 + 남은 경로에 사고 도로 포함 | `vehicles_reroutable` | **우회 판단** | `REROUTE_HOPS=5` (`cctv_detector.py:22`) |
| 그 밖 | — | 없음 | — |

- 한 차에는 명령 하나. 우선순위 **정지 > 우회 > 감속** (`decision_policy.py:30-31`). 정지할 차는 우회를 계산할 여유가 없다고 본다.
- 정체(`congestion_detected`)는 정지 대상이 아니다. 도로 위 차도 감속으로 합친다(`decision_policy.py:56-58`).
- 신양초 보행자 사고만 예외: 스폰 지점이 사고 1칸 앞이라 감속 구간을 없애고(`nearby_hops=0`) 바로 우회 판단. 보행자 지점(도로 시작에서 10m)을 이미 지난 차는 세우지 않는다(`cctv_detector.py:392-401`).

**우회 실행과 "원래 경로 유지" 비교** (`core/vehicle_controller.py:82` `_reroute_around()`)
1. 원래 경로로 가서 사고가 풀릴 때까지 기다리는 경우의 예상 도착 `eta_wait` 계산(`eta_waiting_at()` `:61`).
   = 사고 도로까지 걸리는 시간 → max(도착 시각, 사고 해제 시각) → 사고 도로를 제한속도로 통과 → 나머지.
2. 사고 도로에 통행시간 100만 초 페널티를 30초간 걸고(`:99`, `REROUTE_PENALTY_WINDOW=30.0` `:13`) SUMO에 경로 재계산을 시킨다(`rerouteTraveltime`).
3. 새 경로 예상 도착 `eta_detour`가 `eta_wait`보다 **빠르지 않으면** 원래 경로로 되돌리고(`setRoute`), 그 사고가 끝날 때까지 그 차는 다시 계산하지 않는다(`:103-107`).
4. 예상 도착 계산에서 도로 하나 통행시간은 최대 300초로 자른다(`MAX_EDGE_TRAVELTIME` `:23`). 멈춘 도로는 SUMO 추정치가 수만 초로 튀기 때문(실측 35,920초).
- 켜기/끄기: 환경변수 `SUMO_KEEP_ROUTE=0`이면 끔(`:16`). 기본 켬.

### [SUMO] 3-3. 경로 재계산 두 가지

**(a) 실시간 경로 재계산** (`core/central_server.py:31` `initial_optimization()`)
- 모든 차(실물 보드 차 제외)를 **60초마다**(`REOPTIMIZE_INTERVAL=60.0` `:20`) `rerouteTraveltime`으로 다시 계산. 기준은 SUMO가 매 순간 측정하는 도로별 현재 평균 통행시간.
- 이유: 사고 대응은 사고 주변만 본다. 도시 곳곳에서 서서히 쌓이는 정체는 이것이 담당(`central_server.py:13-19` 주석).
- 60초인 이유 `[가정]`: 차량당 전역 최단경로 탐색이 약 10ms라 7,200대를 자주 돌리면 시뮬레이션이 버벅인다(`predictive_reroute.py:31-32` 주석의 실측). 1분이면 정체 변화 속도에 비해 충분하다고 판단. 다른 주기와 비교 실험은 안 함 `[확인 필요]`.

**(b) 정체 예측 선제 우회** (`core/predictive_reroute.py:73` `_predict_and_reroute()`)
1. 60초마다(`PREDICT_INTERVAL` `:17`) 모든 차의 남은 경로에서 **앞으로 90초 안**(`PREDICT_HORIZON` `:18`, 차당 최대 25개 도로) 도착할 도로별 차 수를 모은다.
2. 도로 용량 = 차선 수 × 0.4대/초(시간당 1,440대, `SATURATION_FLOW_PER_LANE` `:21`) × 90초. 도착 예정이 이보다 많으면 "넘칠 도로"(`:106`).
3. 그 도로에 도착하기까지 **45초 이상 여유**(`MIN_LEAD_TIME` `:20`)가 있는 차만 후보. 가까이 온 차는 대안도 같이 막혀 있을 가능성이 커서 제외.
4. 여유가 적은(급한) 차부터 최대 120대(`MAX_REROUTES_PER_CYCLE` `:35`)만 재계산. 넘칠 도로엔 60초 페널티(`:132`).
5. **몰림 방지**: 같은 대체 도로에 차선당 15대(`MAX_DETOUR_SHARE_PER_LANE` `:43`) 넘게 배정되면, 그 차에게만 그 도로를 피하게 해 다시 계산(`setAdaptedTraveltime` `:161`). 실측 한 사이클 73대 중 71대(97%)가 한 도로로 몰리던 것을 56%로 낮춤(HANDOFF O-D).
- 용량 0.4대/초/차선 `[가정]`: 교통공학의 포화교통류율 대략값(시간당 1,400~1,900대/차선)의 보수적인 쪽. 실측 보정은 안 함.

6. **보드 → 시뮬레이션 합류** (`_release()` `:476`): 보드 차가 도착(`arrived`)하거나 사거리를 지난 뒤 인식이 끊기면, 같은 자리·같은 그림의 **일반 차량 `rc_…`**로 바꿔 넣는다. 목적지는 1.5km 이상 떨어진 무작위 도로. 이제 이 차는 3-2~3-5 중앙 제어를 다른 차와 똑같이 받는다.

```python
    s_b = project_to_polyline(r["board"], (x, y))   # 보드 주행선 위 진행 거리(m)
    d = piecewise_map(r["pairs"], s_b)              # 기준점 쌍으로 SUMO 경로 거리로 보간
    px, py, angle = point_at(r["poly"], d)          # SUMO 좌표·방향
```

```python
traci.vehicle.setSpeed(car["sumo_id"], 0)                                 # SUMO가 몰지 못하게
traci.vehicle.moveToXY(car["sumo_id"], "", lane, x, y, angle, keepRoute=1)  # 실물 위치에 놓기
```

## [SUMO] 7. 예상 킬러 질문과 답변

### [SUMO] Q01. [원리] 왜 SUMO를 썼나? 다른 시뮬레이터(VISSIM, CARLA)는?
1. **짧은 답**: 무료 오픈소스이고, 실제 지도(OSM)를 바로 도로망으로 바꿀 수 있으며, 파이썬으로 매 초 모든 차를 제어(TraCI)할 수 있어서입니다. 학계 교통 연구 표준 도구입니다.
2. **상세**: VISSIM은 상용이고 라이선스 비용이 큽니다. CARLA는 자율주행 센서 시뮬레이션(차 몇 대 수준)용이라 차 7,200대 도시 규모에는 맞지 않습니다. SUMO는 광진구 전체 차도 약 1만 8천 구간을 한 PC에서 돌립니다.
3. **더 파고들 때**: 미시 시뮬레이터라 차 한 대 거동(가속, 차간 거리, 차선 변경)을 계산합니다. 차량 모델은 SUMO 기본(Krauss)이고 보정(캘리브레이션)은 안 했습니다.

1. **짧은 답**: 차량 호스트가 초당 10번 보내고, SUMO는 매 스텝 가장 최신 메시지를 반영합니다. 실물 연결 중에는 시뮬레이션을 실제 시간(1초=1초)으로 돌립니다.

3. **더 파고들 때**: 끝에서 끝까지 지연 실측은 안 했습니다 `[확인 필요]`. 구조상 0.1초 메시지 주기 + 최대 1스텝(1초)입니다 `[가정]`.

### [SUMO] Q22. [확장] 차량이 더 많아지거나 도시가 커지면?

### [SUMO] Q23. [독창성] 카카오내비·T맵 같은 실시간 내비와 뭐가 다른가?

## [SUMO] 8. 다른 파트 사람이 대신 답할 때 주의할 점

**절대 틀리게 말하면 안 되는 것**
- 실물 연동은 **차량 → SUMO 한 방향**. SUMO는 실물 차에 명령하지 않는다. 실물의 정지·후진·우회는 **RC카 제어기가 판단**.
- **"도시 전체 교통이 X% 좋아졌다"고 말하지 말 것.** 공식 실험은 유의미한 차이 없음(5-2). 큰 개선은 도로망 구조 수정(5-3) 쪽이고, 그것도 중앙 제어 효과가 아니다.
- 예선 보고서 수치(TSTT -3.1%, 대기 -5.9%, 충돌 -20.3%)는 **무효**. 버그와 표본 3개 때문.
- 수요는 **무작위**, 실제 교통량 아님. 사고는 **30초마다 인위적으로** 냄.
- CCTV 감지는 **완벽 감지 가정**(영상 인식 아님). 비전(YOLO)은 실물 보드에만 있다.
- 견인은 **양쪽 조건에 똑같이** 적용.
- 신호 197개 중 84곳은 **수동 지정**(OSM에 없음).

**자주 헷갈리는 것**
- "칸(hop)" = 도로 한 토막, 거리(m)가 아님.
- `hwtwin_…` = 보드 위 실물 차(중앙 제어 안 받음). `rc_…` = 보드에서 나와 일반 차량이 된 실물 차(중앙 제어 받음).
- "원래 경로 유지" = 우회 경로를 찾았지만 기다리는 게 빨라서 안 돈 것(판단 실패가 아님).
- 대시보드 카드의 "차량 수" = CCTV 구역 도로 기준. 상세 창의 "화면 안 차량" = 200m 화면 안 전체.

**이 질문이 오면 넘길 사람**
- YOLO 인식 정확도·학습 데이터 → 비전 담당
- RC카 주행 판단 규칙(정지선, 후진, 우회 조건)·모터 제어 → RC카 제어 담당
- 보드 제작·LED·카메라 설치 → 하드웨어 담당
- UDP 메시지 형식 결정 과정 → 연동 규격 담당(`INTERFACE.md`)
- 시뮬레이션·알고리즘·대시보드·수치 → SUMO 담당

## [SUMO] 9. 용어집

- **감속(decelerate)**: 사고 1~2칸 앞 차를 5 m/s로 늦추는 명령.
- **견인(tow)**: 180초 넘게 낀 차를 지우는 현실 보정 (stuck vehicle removal).
- **교차점 합치기**: 쪼개진 사거리 노드를 하나로 만드는 도로망 설정 (junctions.join).
- **그리드락**: 한 교차로에 들어오는 2개 이상 방향이 동시에 60초 넘게 정지 (gridlock).
- **급제동**: 가속도 -4.5 m/s² 미만 (emergency brake).
- **누적 대기시간**: 모든 차의 매 초 정지 시간 합 (total wait time).
- **대시보드**: 웹 관제 화면, `http://localhost:5000` (dashboard).
- **디지털 트윈**: 실물 상황을 가상 공간에 실시간 재현 (digital twin).
- **만성 정체**: 한 도로 평균 2 m/s 이하가 120초 넘게 지속 (chronic congestion).
- **몰림(herd effect)**: 우회 차가 한 대체 도로로 한꺼번에 가서 거기가 막히는 현상.
- **보급률**: 중앙 제어를 따르는 차의 비율 (penetration rate). 이 프로젝트는 100% 가정.
- **선제 우회**: 90초 뒤 넘칠 도로를 예측해 미리 돌리는 것 (predictive rerouting).
- **신호 시간 배분**: 대기열 비교로 초록 연장·조기 전환 (queue-based signal control, max-pressure 계열).
- **실시간 경로 재계산**: 60초마다 현재 통행시간 기준 최단 경로 재계산 (periodic rerouting).
- **우회(reroute)**: 사고 도로에 페널티를 걸고 경로 재계산.
- **원래 경로 유지(keep)**: 우회가 대기보다 빠르지 않아 경로를 되돌림.
- **정지(stop)**: 사고 도로 위 차를 세우는 명령.
- **처리량**: 시뮬레이션 중 목적지에 도착한 차 수 (throughput).
- **칸(hop)**: 교차로 사이 도로 한 토막 단위의 거리.
- **통행시간 페널티**: 라우터에 도로가 아주 오래 걸린다고 알려 피하게 하는 방법 (adaptTraveltime).
- **포화교통류율**: 차선 하나가 초록일 때 처리할 수 있는 최대 교통량 (saturation flow).
- **baseline**: 중앙 제어 없는 비교 조건.
- **edge**: 방향이 있는 도로 한 토막(SUMO 용어).
- **event**: 실물 차량 호스트가 보내는 판단 코드(pedestrian_stop, diverting 등).
- **netconvert**: OSM → SUMO 도로망 변환 도구.
- **OD**: 출발지-도착지 쌍 (origin-destination).
- **OSM**: 오픈스트리트맵, 공개 지도 데이터 (OpenStreetMap).
- **seed**: 난수 시작값. 같으면 같은 결과.
- **SUMO**: 오픈소스 미시 교통 시뮬레이터 (Simulation of Urban MObility).
- **TraCI**: 실행 중인 SUMO를 파이썬으로 제어하는 API (Traffic Control Interface).
- **traffic_state**: 차량 호스트 → SUMO로 보내는 UDP 메시지.
- **treatment**: 중앙 제어를 켠 조건.
- **TSTT**: 모든 차가 도로 위에 있던 시간 합, 도착 못 한 차 포함 (total system travel time).
- **V2N**: 차량-네트워크 통신 (Vehicle-to-Network).
